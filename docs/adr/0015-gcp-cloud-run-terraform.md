# ADR-0015: The presentation environment runs on Google Cloud Run, defined in Terraform

**Status:** Accepted · **Date:** 2026-09-29 · **Deciders:** TODO (team)

## Context

[ADR-0008](0008-cpu-inference-deployment.md) (amendment of 2026-09-29) keeps a presentation environment for the team and leaves the hosting platform open. The only deployment path so far, `deploy.yml` over SSH to a Docker host, has never run: no host, Environment or secret exists ([deployment.md](../deployment.md), section 6). The code freeze is 2026-10-04.

Several guarantees of the other ADRs are written in the terms of the compose file, and a platform has to provide each of them some other way:

- the `core` network is internal and has no egress, and only `banking-core` sits on both networks ([ADR-0004](0004-trust-boundary.md), [ADR-0006](0006-single-postgres-pgvector.md));
- only the orchestrator and the customer web client publish a port, on `127.0.0.1`, and the back office publishes none ([ADR-0013](0013-front-ends-bff-takeover.md));
- the model server receives raw customer text and runs only inside the team's network ([ADR-0008](0008-cpu-inference-deployment.md), amendment 2);
- the embedding model's weights live in a cache volume filled by `make warmup-retrieval` (the fine-tuned DistilBERT of [ADR-0014](0014-distilbert-intent-backend.md) is already in the encoder image);
- each service receives only its own environment; there is no shared `.env`.

## Decision

**The presentation environment runs on Google Cloud Run in `us-east1`, and everything it needs is defined in Terraform under `infra/deploy/gcp/`.** The compose file stays the way to run the system locally and the way judges run it (`make demo`).

| Guarantee | Compose | Cloud Run |
|---|---|---|
| `core` has no egress | `internal: true` network | `core` subnet with no Cloud NAT; Google APIs through Private Google Access |
| Only `banking-core` reaches Postgres and redis-core | Network membership | Network tags on Direct VPC egress; a firewall rule denies `pb-edge` egress to the `psa-core` range where Cloud SQL and redis-core live |
| One Redis per zone, each with its own password | Two containers, `--requirepass` | Two Memorystore Basic instances with AUTH, in separate private-service-access ranges |
| Backends not reachable from outside | No published port, or `127.0.0.1` | Ingress `INTERNAL_ONLY`; callers reach them through the VPC |
| Back office not published | No `ports` | Identity-Aware Proxy on the service; only listed team accounts get through, then its own login |
| The model server has no path out | Not stated today | `edge` subnet with no Cloud NAT; only the orchestrator's `egress` subnet has NAT, for the LLM provider |
| Each service gets only its own secrets | Per-service `environment:` | One service account per service, with access to exactly the Secret Manager secrets its compose block lists |
| Model weights present at start | `hf-cache` volume for the embedding model; DistilBERT in the image | Both in the encoder image: the embedding model baked in at build time, pinned by revision and hash; the DistilBERT copied from its seed image by digest ([ADR-0014](0014-distilbert-intent-backend.md)) |
| Which decision model serves | `DECISION_POINTS_FILE` in `.env.example` | The same artifact, through the `decision_points_file` variable; a test keeps the two equal |
| One-off migrate and seed | `docker compose run` | Cloud Run Jobs on the `banking-core` image, in the `core` subnet |

Around it:

- **Terraform owns the infrastructure and the service configuration; CI owns the image.** Terraform ignores image changes after creating a service; `deploy.yml` builds to Artifact Registry, runs the migrate job and rolls each service to the new image. GitHub holds no secret: it logs in through Workload Identity Federation, bound to one repository id, branch and workflow file, all variables.
- **Secrets are generated by Terraform** (master key, blind-index salt, session and back-office secrets, the two API tokens, the demo password, the database and Redis passwords). The LLM key is the only one added by hand.
- **The decision model is the one the local stack runs.** The encoder serves the pooled DistilBERT artifact of [ADR-0014](0014-distilbert-intent-backend.md), not the code's `tfidf_lr` default. Its kill switch back to `tfidf_lr` is the `decision_points_file` variable and an apply, not a code change or a new image: the baseline's artifact and train data are in the same image.
- **Warm by default for a presentation.** The encoder, `banking-core` and the orchestrator keep one instance running, the encoder with CPU always allocated; a `warm` variable sets every minimum to zero between presentations.
- **Two stopgaps, both declared in [limitations](../limitations.md):**
  - Behind Google's front end the web-client BFF cannot see the customer's address, so the orchestrator runs with `TRUSTED_PROXY_HOPS=0` and a high per-address limit until the BFF forwards the client address.
  - The backends are protected by internal ingress, not by IAM identity tokens. Anything inside the project's VPC can call them.
- **The SSH path is removed.** One deployment path, exercised, beats two that never ran.

## Options considered

### Option A: a Docker host over SSH (the existing `deploy.yml`)

**Pros:** everything already written; the compose guarantees carry over unchanged; one small VM costs about $3–4 a day.
**Cons:** never exercised; the team administers a host (patches, disk, Docker, the reverse proxy and TLS); one host is one failure domain; secrets are written to a file on it.

### Option B (chosen): Cloud Run with managed data services

**Pros:** no host to administer; TLS, revisions and rollback come with the platform; every guarantee above has a managed equivalent; secrets never leave Secret Manager; the whole environment is reproducible from one `terraform apply`.
**Cons:** more to build before the freeze (network, IAM, IAP, the deploy job); cold starts unless instances are kept warm, which costs about $8–11 a day; Direct VPC egress and Cloud NAT add start-up delays.

### Option C: GKE Autopilot

**Pros:** closest to the compose model (pods, network policies, volumes).
**Cons:** a cluster to learn and operate for five services, a week before the freeze. Nothing here needs it.

## Trade-off analysis

Option A is cheaper to write and B is cheaper to run well. The deciding factor is that A's guarantees are only as good as the host the team has to keep healthy during the presentation, while B's are properties of managed resources that a test can check before anything is deployed. The price is build time now and a daily cost that the `warm` switch keeps bounded.

## Consequences

**Becomes easier:** rolling back (a previous revision), rebuilding the environment from zero, and checking the trust boundary: Terraform tests assert the secret-access matrix, ingress, tags and firewall offline, and a network-check job proves the firewall live.

**Becomes harder:** the presentation environment now depends on a cloud account and its billing; a first deploy needs a GCP project, an OAuth client for IAP when the project has no organization, and repository variables.

**Given up:** the model server and the backends are reachable by anything inside the VPC, not only by their callers; the secrets are in Terraform's state, so the state bucket is as sensitive as the secrets; Cloud SQL is single-zone and Redis has no TLS.

**Not changed:** the local stack, `make demo` and every contract. No application code changes except that the encoder image can bake its weights and the back office's idle timeout follows its upstream timeout.
