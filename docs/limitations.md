## 2. What works with caveats

| Capability | Caveat |
|---|---|
| Document verification | Simulated provider; the interface is real, the verification is not ([ADR-0007](adr/0007-no-llm-biometrics.md)). The simulator is deterministic and driven by the opaque `document_front_ref`: `sim-approve-*` returns APPROVED, `sim-reject-*` returns REJECTED, and any other ref returns MANUAL_REVIEW_REQUIRED (no provider result, a human decides). The tool only reports a decision and never changes the verification state |
| Outbound OTP channel | Decided ([ADR-0007](adr/0007-no-llm-biometrics.md), amendment 2026-09-29): the OTP is **not** sent by email, SMS or any other external channel. `banking-core` delivers through `OtpDeliveryPort` to a simulated inbox on redis-core, and the web client (`apps/web-client`) shows it as "you got an email with the code": one read of the inbox after each turn, a countdown to expiry, and the code only after "Show code". The demo customers are registered on email and the blocked-card ones on sms, both simulated the same way. `OTP_CHANNEL_MODE=simulated` is the only mode implemented; any other value stops `banking-core` at startup with an explicit message. The model never sees the code and never chooses the channel or destination. **Caveat: whoever sees the browser sees the code.** The browser that shows the notice is the one that types it, so in the demo the OTP does not prove possession of the registered channel, and since the code travels through the orchestrator to the browser it no longer protects against a compromised orchestrator. A real provider restores both by implementing the port; none exists, and choosing one is a new ADR |
| Key management | Master key from the environment, not from a KMS ([ADR-0005](adr/0005-application-level-encryption.md)). On Cloud Run ([ADR-0015](adr/0015-gcp-cloud-run-terraform.md)) Terraform generates it and it reaches `banking-core` from Secret Manager, but it is also in the Terraform state: the state bucket is as sensitive as the key |
| Second workflow | Added by configuration ([ADR-0002](adr/0002-config-code-boundary.md) amendment of 2026-09-29): `account.get_summary` starts disabled (`POLICY_SEED_DISABLED_TOOLS`) and is enabled live through the versioned tool policy (`PUT /v1/admin/tool-policy`, audited, never beyond the code floor). It only recombines tools already in the catalog; a new banking operation is code. Covered by the `account_inquiry` scenarios (8, three with the tool disabled), not the full suite, and those scenarios have not been run against a model yet (`make eval` is pending, no replay recordings exist). Every catalog tool is still offered to the model whatever the policy says (the orchestrator does not read it), so a disabled tool is found by a refused call that the model must explain; nothing checks the wording of that reply automatically. It is toggled from the tool matrix of the back office's Guardrails screen, or with the admin API call in the [runbook](runbook.md). The floor is a ceiling, not a minimum: the same call can switch off any tool, `handoff.create` included |
| Detective mode | Each chat turn's masked timeline, behind a switch in the chat ([ADR-0019](adr/0019-detective-mode.md)); on locally, opt-in on production and Cloud Run (`detective_mode`, set in `presentation.tfvars`, not yet deployed). **It shows whoever uses the chat the system prompt, the tools offered and the policy outcomes.** Gaps: a failed turn (LLM error, replay miss) returns no trace; traces are not stored, so a reload shows none; a turn answered during a takeover adds no reply, so its trace is not shown; the back office does not show traces; retrieval internals (keyword and embedding scores, candidates) and policy internals stay in banking-core; the masking of the assistant's stored reply is not a step of the trace (a word it masks there shows up only as a placeholder in the next turn's prompt); the panel's view and picked turn are not remembered |
| Multi-tenancy | Anticipated in the data model, not implemented |
| Multi-replica scaling | Orchestrator and banking-core keep no local state (externalized to Redis and Postgres) and use distributed locks, fenced saves and idempotency keys, but the system has not been load-tested or run with more than one replica ([docs/deployment.md](deployment.md)) |
| Per-replica memory overhead | Each banking-core replica still builds the 120-snippet KB index in memory (pgvector table ingestion is pending), but from vectors the model server returns: the embedding model itself (~1.3 GB RSS with the index, measured on macOS) is loaded once on the model server, not per replica. `BANKING_CORE_MEMORY_LIMIT` stays `2g` until a Linux measurement exists. Migrations and seed run once, not per replica. GLiNER requires ~4 GB RSS, so `.env.example` seeds `ENCODER_BACKEND=tfidf_lr` ([docs/deployment.md](deployment.md)) |
| Audit log external anchoring | Hash chain integrity is enforced append-only in Postgres with triggers and verified via `make verify-audit` (which reports row count and head hash); external anchoring of the head hash (e.g. to a timestamping authority, transparency log, or external store) to detect tail truncation is pending. |
| Outbound PII masking | The text sent to the LLM masks the **union** of the regex matches and the encoder's PII spans (`orchestrator/privacy/spans.py`); every outbound string is masked and verified, and a failure sends nothing. If the encoder is unavailable the customer's text is masked by the regexes alone, never by less, and the turn metadata says so (`masking_regex_only`). Regexes cover emails, card numbers, documents, phones, one-time codes, names after an intro phrase or salutation, and dates numeric or written out in es/pt/en ("4 de marzo de 1988", "March 4, 1988", "4 mar 1988"). **Known misses:** names without an intro phrase ("hola, Carlos Gómez aquí") are caught only when the `gliner` backend runs, because `tfidf_lr` (the demo default) has no name, phone or document spans; digit groups split by spaces; written dates without a year, month plus year, two-digit years and dates in words ("cuatro de marzo"); addresses, merchant names, amounts and card last four are not treated as PII; languages other than es, pt and en. The encoder's spans are trusted as character offsets into the text it was sent: they are widened to whole words and can only add masking, but a span that widens a regex match under another type gives the larger span's type (a `[DOC_n]` can become a `[NAME_n]`, which only costs the model that value), and one that cannot be placed exactly makes the turn ask the customer to rephrase. Replay keys hash the masked text, so recordings must be made and replayed with the same encoder backend: a backend with more spans changes the text and misses the recording. The provider and its data residency: see "Single LLM" below |
| Knowledge retrieval evaluation | Measured on a **provisional synthetic** query set (120 validation queries per language, `data/eval/synthetic/retrieval/`), not a human-written one. Vector-only is the default backend, on `granite-embedding-311m-multilingual-r2` since 2026-10-01 (same-language Hit@1 0.719, cross-language 0.711, vs MiniLM 0.494 / 0.508 and BM25 0.366 / 0.144; [ADR-0006](adr/0006-single-postgres-pgvector.md), amendment 2026-10-01). A second, harder **provisional** set grounded in real es-MX, es-AR, es-CO and pt-BR language (`queries_regional.jsonl`, 600 GPT Sol questions, **not reviewed by a human**; `reports/embedding-regional-2026-10-02.md`) confirms Granite in every locale. On the production path, Hit@1 0.55 searching the orchestrator LLM's `kb_query`, against 0.36 on the raw message. 68 of its 540 answerable questions may carry the wrong topic (listed in its `checks.md`). A second set from the same recipe, written by hand by Claude Opus 5.5 (`queries_regional_claude.jsonl`), keeps the ranking but moves absolute Hit@1 by up to 0.18 (`reports/embedding-regional-claude-2026-10-02.md`): read any single number as describing its set, not production. Its author also built the pipeline and had seen the KB and part of the first set. The evaluation forces a `kb_search` call even for small talk, which inflates off-topic leakage on the LLM-query path (20% at 0.81 on the Claude set). English has no regionally grounded set. The score floor (0.81) still separates answerable from off-topic questions by a few hundredths: at 0.81, 8% of off-topic questions get snippets and 7% of out-of-scope banking questions lose the scope snippet. A human-written set with out-of-scope questions must re-derive it. Banking-core `kb.search` serves the in-memory `packages/retrieval` index, built from vectors the model server returns (see "kb.search footprint"); pgvector ingestion remains pending. |
| Bare OTP in customer text | While an OTP challenge is pending, any standalone 4-8 digit run in the customer text is masked as an OTP (a small amount typed at that moment is over-masked, on the safe side). Outside a pending challenge, the regexes do not mask a bare code without a cue ("123456"); with the encoder up, `tfidf_lr` flags a lone six-digit number in a message of four words or fewer as a one-time code, so a six-digit amount typed alone is masked too (the safe side) |
| Encoder signal in the turn engine | The encoder runs first, on the raw customer text over the edge network (a local service, not a provider). The turn metadata records its intent, confidence and abstention, and only counts of its PII spans (`encoder_pii_spans`, `encoder_spans_added`; never offsets or text); its intent is not fed to the LLM (the decision points below ride on the same call and reach the LLM only as the categorical `CONFIRMATION_REQUIRED` refusal, and only when the gate enforces; the `hint` effect of ADR-0014 can pass the decided intent as one categorical system line, but it ships in `shadow`, so today nothing more reaches the LLM). Its PII spans widen the masking (see "Outbound PII masking"). Any encoder failure (unavailable, timeout, invalid payload, unexpected error) leaves the turn masked by the regexes alone and sets `encoder_unavailable` and `masking_regex_only`; with `ENCODER_ENABLED=false` the same masking is by configuration, not a degradation. Texts over 2,000 characters are outside the encoder contract and take the same path |
| Single LLM (GPT 6 Luna) | One model was chosen for the submission ([ADR-0001](adr/0001-cheap-llm-specialized-encoder.md), amendment 2026-09-29) for cost, tool support and access to a key, before any comparison existed. The comparative evidence came later and is narrower than `make eval`, which is still not wired: the LLM bench ([reports/llm-flow-stages-2026-10-02.md](../reports/llm-flow-stages-2026-10-02.md)) and one live end-to-end run each of luna and the local Qwen3.6-35B-A3B (`make eval-live`, [luna](../reports/eval-live-2026-10-02-gpt-6-luna.md): 36 of 58 scenarios, 0 unsafe, about $0.0005 per conversation; [Qwen](../reports/eval-live-2026-10-02-qwen3.6-35b-a3b-think.md): 35 of 58). One run each, not replayable. The DeepSeek candidates are future work. It needs reasoning effort `none` to accept temperature 0; the `LLM_REASONING_EFFORT` setting is pending in PR #1 (`feat/llm-reasoning-effort`), and the model id and key are configured by the teammate who owns them. Masked conversations go to a US provider: a cross-border transfer with no data-processing agreement, retention or training-use terms reviewed, and no regional processing or zero-retention option in use. Replay recordings are keyed by model id and must be recorded with this model |
| Local LLM benchmark (`tools/llmbench`) | Run once (2026-10-02, one repeat, [reports/llm-bench-2026-10-02.md](../reports/llm-bench-2026-10-02.md)): four local models on a network RTX 3090 and the hosted gpt-6-luna and gpt-6.1-sol as the upper bar. gpt-6.1-sol ran at temperature 1 (it has no `none` reasoning effort), so its numbers are not deterministic. At that first run, only gpt-6.1-sol walked identify → OTP → verify → block unaided (9 of 9 flows; luna 4, local models at most 1), because nothing the model saw named the verification step. The flow hint ([ADR-0016](adr/0016-banking-core-states-the-next-step.md)), the generated tool descriptions and prompt `turn-engine/4` were then measured stage by stage ([reports/llm-flow-stages-2026-10-02.md](../reports/llm-flow-stages-2026-10-02.md)): luna completes 10 of 12 flows, against 3–4 before; of the local models, only Qwen3.6-35B-A3B with thinking on (it fits a 24 GB card) reaches luna's 10 of 12; without thinking it gets 7, and the best small one, Granite 4.2 3B, gets 6. Open from that run: luna proposes `customer.match` before the customer has given a document (the engine refuses each one; since 2026-10-04 the `customer_match` description says to ask first, and a round that only reached for identification while the session is ANONYMOUS and no document was given ends with a fixed identity request instead of the model's reading of the refusal; its opening names the request, by the tool the model reached for or else the enforced `intent_hint` intent, and only when banking-core enables the tool that serves it (neutral otherwise: a fixed text covers card protection, a charge, recent transactions and the balance, nothing else); not re-measured on the bench), and a hint before the first turn is untested. What it measures is narrower than `make eval`: the real `TurnEngine` and `LLMProvider` (masking, guards, required handoff, block allowlist) run against a **sandbox bank**, which reuses banking-core's authorizer, FSM, amount policy, handoff rules and demo fixtures but keeps the data in memory: no Postgres, audit chain, encryption, Redis or cross-session attempt limits, and a deterministic OTP. It runs **without the encoder**, so masking is by regexes alone and `intent_hint` / `clarify_route` do not act: models get less help than in production. The 30 skill probes are synthetic and single-author, one per skill and language; the reply-language check is a stopword heuristic and the block-claim check is evalrunner's U5 regex, which can misread a negated sentence. Its numbers are evidence for choosing a model, not system evidence: run files stay in `tools/llmbench/results/` (gitignored), and evalrunner's guard keeps them out of `reports/` unless a comparison is published on purpose (`make llm-bench-compare PUBLISH=1`) |
| Decision test split | Provisional: `decision.test.provisional.jsonl` was written free-form by an AI agent, not by humans, and has no double labeling. Calibration reports on it carry a "provisional synthetic (not human)" banner. The human set per [labeling-rubric.md](labeling-rubric.md) replaces it |
| Regional decision datasets (pt-BR, es-MX, es-AR, es-CO) | Built by `tools/synthdata_regional` (`make synth-data-regional`, `build-test-regional`, `check-data-regional`). Each has 100 train, 50 validation and 50 test rows per intent. Limits: **no human review**, and automated checks are the only quality evidence (`checks.md` per locale). Train and validation are LLM-written (gpt-6.1-sol). The test splits were hand-written by the coding agent and are provisional. The es-MX and es-AR test splits share scenarios with each other. The real-world check sets (300 BR complaints, 150 reviews per Spanish country) carry the agent's silver labels (`lab/complaints-labeling-notes.md`). The Spanish sources are app-store reviews, not chats, and mostly about the app. Card intents have very little real evidence: lost card has 7 MX sentences and 2 AR, and unrecognized charge has 5 AR, so those intents rely on the rubric definitions. **The datasets stay local:** `data/staging/` is not versioned, so the numbers can only be reproduced from the LLM cache in `lab/.cache/llm/` or by paying for new calls. **es-CO** (2026-10-01) comes from 618 tuquejasuma.com complaint texts about five Colombian banks (`make stage-data-co`): a forum, not app reviews, with only 105 theme-tagged sentences for generation and almost none for card intents, so its Colombian flavour is mostly register and regional words. The staging name scrub and the site's masks still miss some names and partial emails in the raw text; none appear in the phrases sent to the generator |

| Encoder abstention calibration | **Legacy seed mode only:** the committed calibration artifact (`packages/encoder/calibration/decision_points.json`, see the decision-point rows below) supersedes `ABSTENTION_THRESHOLD`, which the encoder then ignores and logs; the rest of this row is what holds when no artifact file exists. Calibrated threshold tau is required before serving live traffic ([ADR-0010](adr/0010-model-selection-calibration-harness.md)). The seed value 0.37 is the highest per-language tau of `tfidf_lr` in `reports/calibration-decision-2026-09-28.md`, chosen on validation. On the provisional test split it does **not** hold the 0.90 per-class precision target (worst class 0.32 es, 0.53 pt, 0.40 en; macro-F1 0.79/0.84/0.79), so the encoder output is advisory only: the FSM and the policy engine decide ([ADR-0003](adr/0003-deterministic-vs-ai.md)). | Encoder backends | `tfidf_lr` (lexical baseline) returns intents plus regex slots (email, card number, card last 4, OTP, amount, currency, dates) and PII spans for the PII-typed ones (email, card number, OTP, birth date); names, phones, document numbers, document types and merchants need `gliner`. The regex rules were tuned on the synthetic train and validation splits, and the provisional test split has the same author as the rules, so regex slot scores on it are optimistic until the human test set exists. `gliner` refuses to start when the cgroup memory limit is below `ENCODER_GLINER_MIN_MEMORY_MB` (default 4096); an unreadable or unlimited cgroup starts with a warning. `gliner` maps PII-typed slots to PII spans. Measured with `make encoder-bench` on the synthetic validation split (450 messages, single thread, Apple M-series host, 2026-09-27): `tfidf_lr` build 0.15 s, p95 0.22 ms, +43 MB RSS; `gliner` (`fastino/gliner2.5-multi-v1`, fp32) build 18 s, p95 90 ms, peak RSS 3.45 GB. The default demo backend is `tfidf_lr`; `gliner` needs `ENCODER_MEMORY_LIMIT=4g` (the compose default stays 3g), and `ENCODER_QUANTIZED` is read by compose but not implemented. The GLiNER weights of the legacy `ENCODER_BACKEND=gliner` path come from the Hugging Face cache by model id, without a pinned revision or hash yet (ADR-0010 §5); a `gliner` backend named in a decision-point artifact is pinned by revision (and optional hash) and loaded from the verified snapshot only, and on Linux PyTorch comes from the CPU-only index (`pytorch-cpu` in the root `pyproject.toml`; macOS keeps the default wheels for MPS training). The `gliner` image build has not been completed on the dev host yet (Docker disk full) |
| Delivered dataset in the seed | Loaded through `make ingest SOURCE=factored` ([ADR-0011](adr/0011-hybrid-seed-dataset-ingest.md)), capped at 5,000 customers by default (`INGEST_MAX_CUSTOMERS=0` for the full volume). Dates are shifted to end at `INGEST_ANCHOR_DATE`, so the history is realistic in shape but not in calendar. The ARS threshold is a seed derived once from the dataset's exchange rates. Counts per rule in `reports/data-quality-factored.md`. | Admin API | `/v1/admin` uses bearer-token auth; demo fixture resets are disabled in production unless explicitly enabled. | Back-office metrics | `GET /v1/admin/metrics?hours=` counts rows that already exist: tool calls by action, decision and reason code, cards blocked, OTP sent, verified and failed from `ops.audit_log` in the window, and handoffs from `ops.handoff` by status, priority and department. Definitions that matter: a card is *blocked* when an allowed `card.block` moved it to `BLOCKED` from another state (a repeat on a blocked card is a tool call, not a block); an OTP *failed* when an allowed `otp.verify` compared a code and rejected it (a refused call, for a locked customer or a wrong state, is a tool call and never compared a code); handoffs are counted by creation time inside the window, so an older case still waiting does not appear in its counts (the queue shows it). The queries scan the window through the `occurred_at` index and were not load-tested; the previous window runs the same queries a second time. |

| Transactions and balances in the chat | The chat sets the assistant's money apart: a dash list of amounts is a ledger of date, label and amount, and any other amount stays on one line (`apps/web-client/src/app/chat/money-text.ts`). | Agent API and the human takeover | The orchestrator serves `/v1/agent` (read a conversation, take it over, write to the customer) behind one shared bearer token, off unless `AGENT_API_ENABLED=true`. The development compose turns it on with the public token `dev-only-agent-token`; the orchestrator refuses to start with that token (or an empty one) under `APP_ENV=production`, and the production compose pins it back to off. It shares the orchestrator's port, so the token is its only protection: keep `/v1/agent` off any customer-facing ingress. **Who the agent is comes from the caller** (`agent_ref`, `X-Agent-Ref`); the orchestrator cannot check it. A takeover is one-way: **no hand-back to the assistant**. Its holder can release it when the case is escalated back to the queue ([ADR-0018](adr/0018-agent-decisions-on-a-case.md)): the assistant stays off, nobody writes until the next agent's takeover, and a second agent gets 409 while the first one holds it. The transcript does not record which agent wrote a message, so after a transfer the back office labels earlier agent messages with the current holder. The customer sees the agent's replies by polling the transcript. A takeover and an agent message wait up to `AGENT_LOCK_WAIT_SECONDS` (10) for a customer turn in flight, then answer `503 turn_in_progress`; the caller retries. The conversation and its session index still expire with the session TTL of inactivity, after which the agent cannot read the transcript of a queued handoff |
| Agent text is shown as written | PII an agent types is shown to the customer: "Hola, soy Ana" reads as typed, in both transcripts and in the answer to the write ([ADR-0013](adr/0013-front-ends-bff-takeover.md), amendment 2026-09-29). It is stored **encrypted at rest** (Fernet, keyed by `SESSION_SECRET`, the key of the placeholder map) in `content_enc`, next to the masked `content`, which **stays in clear** in redis-edge and is what a dump shows; whoever holds the key and a dump can read the text, and a rotated key orphans it. The assistant never sees it: the takeover guard shuts the engine, the model's history is `llm_history` (no agent message enters it), and a test clears a takeover by hand to show it. If a ciphertext cannot be read, the masked text is shown with a warning that carries no text. The composer tells the agent the customer sees the text as written and to write only what the customer needs; nothing checks it. The customer app still renders a full card number as `•••• 1234`, whoever wrote it, so a card number an agent types reaches the browser as written and is shown masked. An orchestrator version without the field cannot read a conversation that has an agent message with it |
| Customer text during a takeover | It is masked by the regexes and the conversation's known values only: **the encoder is not called**, so a name or an address the regexes cannot detect stays in clear in the transcript the agent reads (and in redis-edge until the TTL). A code typed into an OTP challenge that was pending when the agent took over is masked as an OTP (any 4-8 digit run, so an amount typed then is over-masked: the safe side); with no challenge pending a bare code is not masked, as before the takeover. No tool runs and nothing re-verifies the customer during the takeover: the banking-core session stays in the state it had when the agent took over |
| Amount guardrail needs the model to link the charge | The amount comes from the database, but only for the `transaction_id` the model passes to `card.block` ([ADR-0003](adr/0003-deterministic-vs-ai.md), amendment 2026-09-29). A `UNRECOGNIZED_CHARGE` or `SUSPICIOUS_ACTIVITY` block without one fails safe into a required handoff. A `LOST`, `STOLEN` or `CUSTOMER_REQUEST` block without one is compared with no amount, so a model (or a customer steering it) that picks such a reason and omits the link is not checked against the threshold. banking-core does not yet look at the card's recent charges by itself, so a model (or a customer steering it) that links a different, smaller real charge of the same card lowers the outcome as well. ## 3. What we did not do

| Not done | Why |
|---|---|
| Autonomous dispute resolution | A judgment call with monetary impact: our test case for not automating |
| Real biometrics | Requires a certified provider with liveness detection |
| Voice channel | A different problem (transcription, latency, barge-in); adds nothing to the chosen workflow |
| Onboarding and credit origination | Outside the workflow |
| Load testing | We prioritized correctness over performance in the available time |
| Per-IP rate limiting in banking-core | Banking-core cannot trust a client address relayed by the untrusted orchestrator; per-IP limiting belongs at the edge, where it exists only for conversation creation (§2) |
| Per-IP limit on messages, and distributed attackers | Sending messages, opening conversations from many addresses, and any attacker with more addresses than the per-IP budget are not limited per address. What bounds them is the per-customer and per-document limits (a fixed number of OTP guesses per customer and of match guesses per document, however many addresses guess) and the per-session limits. No CAPTCHA, no reputation feed, no anomaly detection |
| Limit on `otp.send` volume across sessions | A resend limit exists per session and a locked customer gets no code, but nothing limits how many codes different sessions can trigger for one customer before the lock (unrelated to failed verifies): an SMS-bombing and delivery-cost vector. Needs a per-customer send counter |
| Feedback when the assistant solves the case alone | It needs an end signal the engine confirms (a block or state the model proposes and banking-core accepts), eval scenarios for when it must not fire, and a prompt change ([ADR-0017](adr/0017-assistant-feedback-after-handoff.md)) |
| Hand-back to the assistant | Once an agent takes a conversation ([ADR-0013](adr/0013-front-ends-bff-takeover.md)) the assistant never sees it again; nothing returns it. A customer who wants the assistant back opens a new conversation. Doing it safely needs a rule for what the assistant may know of the human turns, which was not designed |
| Closing and escalating a case | Since [ADR-0018](adr/0018-agent-decisions-on-a-case.md) an agent closes a case (approved, rejected with a reason, or resolved) or escalates it to another department, optionally raising it to urgent; both are audited and refused for a case another agent holds. **No decision moves money or unlocks anything**: a close records the agent's decision, and a refund, a chargeback or an unlock would each be a banking operation with its own tool. The closing message is a fixed text per outcome and language from `banking_core/handoff/decisions.json`, edited by pull request, and does not name the amount or the merchant. A closed case cannot be reopened, an agent cannot un-claim a case without escalating it, and the audit log does not record a refused attempt (a 409 writes nothing). Escalating from the queue does not notify the customer. If the conversation has expired, the case closes and the customer is not told |
| Agent identity is asserted by the back office | `banking-core` authenticates the back-office server with one shared token (`ADMIN_API_TOKEN`) and records the `agent_ref` it is sent as the actor of the claim; it cannot verify who that is. The back office derives it from its own signed session cookie, and the demo has one agent credential (`DEMO_AGENT_EMAIL`), so the audit row is only as trustworthy as that server ([ADR-0004](adr/0004-trust-boundary.md) amendment 2026-09-29 (2)). The claim caps `agent_ref` at 128 characters, the width of `ops.audit_log.actor_ref`, not the 254 of an email address. Per-agent identity that `banking-core` can verify, and SSO, are not built |
| Polling instead of push | The queue, an open conversation and the customer chat from the handoff on are read by polling (3 s, 2 s and 2 s; stopped while the tab is hidden), not by WebSocket or server-sent events; the OTP inbox is not polled, it is read once after each customer turn ([ADR-0013](adr/0013-front-ends-bff-takeover.md)). A change shows after up to that interval, and every open tab adds steady requests; it was not load-tested with many agents. The customer chat polls from the handoff block on, so the agent's first message arrives unprompted; if no agent ever claims the case it keeps polling every 2 s while the tab is visible, with no back-off |

## 4. Known failure modes

**TODO at close.** The ones we already anticipate and must confirm or rule out with data:

- Degradation in Portuguese relative to Spanish in the classifier, if the labeled sample came out unbalanced
- Cross-language retrieval: question in one language, knowledge in another. Measured: vector-only Hit@1 0.508 (mean es/pt/en) against an index restricted to the other languages; BM25 0.144. Same-language search is the default, so this only matters when the KB lacks the customer's language
- Long conversations: context grows and so do cost and latency
- Ambiguity between neighboring intents: TODO, per the confusion matrix
- Unnecessary escalation on legitimate but unforeseen cases: a cost the design accepts ([ADR-0003](adr/0003-deterministic-vs-ai.md))

## 5. What we would do with four more weeks

1. **A real document verification provider**, with thresholds and retry policy.
2. **KMS or HSM** for the master key, with scheduled rotation.
3. **Human-in-the-loop learning**: every agent correction in the back office becomes a labeled example, with periodic retraining and drift monitoring.
4. **Continuous evaluation in production**: sampling real conversations for human review, not just a fixed suite.
5. **Load testing and a read replica** before exposing the system to real volume.
6. **Expand the adversarial suite**, with injection in fields we do not currently treat as hostile.
7. **Full multi-tenancy** on top of the schema separation already anticipated.

## 6. Where else this applies

The engine is not banking-specific. The same core — calibrated classification with abstention, verification state machine, policy engine, structured handoff and audit — applies to any customer service domain where an action has irreversible consequences: telecommunications, insurance, healthcare, logistics. What changes is the tool catalog; the control does not.
