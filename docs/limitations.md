## 2. What works with caveats

| Capability | Caveat |
|---|---|
| Document verification | Simulated provider; the interface is real, the verification is not ([ADR-0007](adr/0007-no-llm-biometrics.md)). The simulator is deterministic and driven by the opaque `document_front_ref`: `sim-approve-*` returns APPROVED, `sim-reject-*` returns REJECTED, and any other ref returns MANUAL_REVIEW_REQUIRED (no provider result, a human decides). The tool only reports a decision and never changes the verification state |
| Outbound OTP channel | Decided ([ADR-0007](adr/0007-no-llm-biometrics.md), amendment 2026-09-29): the OTP is **not** sent by email, SMS or any other external channel. `banking-core` delivers through `OtpDeliveryPort` to a simulated inbox on redis-core, and the web client shows it as "you got an email with the code" (⚠️ pending UI; the banking-core and orchestrator endpoints exist). The demo customers are registered on email and the blocked-card ones on sms, both simulated the same way. `OTP_CHANNEL_MODE=simulated` is the only mode implemented; any other value stops `banking-core` at startup with an explicit message. The model never sees the code and never chooses the channel or destination. **Caveat: whoever sees the browser sees the code.** The browser that shows the notice is the one that types it, so in the demo the OTP does not prove possession of the registered channel, and since the code travels through the orchestrator to the browser it no longer protects against a compromised orchestrator. A real provider restores both by implementing the port; none exists, and choosing one is a new ADR |
| Key management | Master key from the environment, not from a KMS ([ADR-0005](adr/0005-application-level-encryption.md)) |
| Second workflow | Added by configuration ([ADR-0002](adr/0002-config-code-boundary.md) amendment of 2026-09-29): `account.get_summary` starts disabled (`POLICY_SEED_DISABLED_TOOLS`) and is enabled live through the versioned tool policy (`PUT /v1/admin/tool-policy`, audited, never beyond the code floor). It only recombines tools already in the catalog; a new banking operation is code. Covered by the `account_inquiry` scenarios (8, three with the tool disabled), not the full suite, and those scenarios have not been run against a model yet (`make eval` is pending, no replay recordings exist). Every catalog tool is still offered to the model whatever the policy says (the orchestrator does not read it), so a disabled tool is found by a refused call that the model must explain; nothing checks the wording of that reply automatically. The back-office toggle is pending: until then it is the admin API call in the [runbook](runbook.md). The floor is a ceiling, not a minimum: the same call can switch off any tool, `handoff.create` included |
| Multi-tenancy | Anticipated in the data model, not implemented |
| Multi-replica scaling | Orchestrator and banking-core keep no local state (externalized to Redis and Postgres) and use distributed locks, fenced saves and idempotency keys, but the system has not been load-tested or run with more than one replica ([docs/deployment.md](deployment.md)) |
| Per-replica memory overhead | Each banking-core replica still builds the 120-snippet KB index in memory (pgvector table ingestion is pending), but from vectors the model server returns: the embedding model itself (~1.3 GB RSS with the index, measured on macOS) is loaded once on the model server, not per replica. `BANKING_CORE_MEMORY_LIMIT` stays `2g` until a Linux measurement exists. Migrations and seed run once, not per replica. GLiNER requires ~4 GB RSS, so `.env.example` seeds `ENCODER_BACKEND=tfidf_lr` ([docs/deployment.md](deployment.md)) |
| Audit log external anchoring | Hash chain integrity is enforced append-only in Postgres with triggers and verified via `make verify-audit` (which reports row count and head hash); external anchoring of the head hash (e.g. to a timestamping authority, transparency log, or external store) to detect tail truncation is pending. |
| Outbound PII masking | The text sent to the LLM masks the **union** of the regex matches and the encoder's PII spans (`orchestrator/privacy/spans.py`); every outbound string is masked and verified, and a failure sends nothing. If the encoder is unavailable the customer's text is masked by the regexes alone, never by less, and the turn metadata says so (`masking_regex_only`). Regexes cover emails, card numbers, documents, phones, one-time codes, names after an intro phrase or salutation, and dates numeric or written out in es/pt/en ("4 de marzo de 1988", "March 4, 1988", "4 mar 1988"). **Known misses:** names without an intro phrase ("hola, Carlos Gómez aquí") are caught only when the `gliner` backend runs, because `tfidf_lr` (the demo default) has no name, phone or document spans; digit groups split by spaces; written dates without a year, month plus year, two-digit years and dates in words ("cuatro de marzo"); addresses, merchant names, amounts and card last four are not treated as PII; languages other than es, pt and en. The encoder's spans are trusted as character offsets into the text it was sent: they are widened to whole words and can only add masking, but a span that widens a regex match under another type gives the larger span's type (a `[DOC_n]` can become a `[NAME_n]`, which only costs the model that value), and one that cannot be placed exactly makes the turn ask the customer to rephrase. Replay keys hash the masked text, so recordings must be made and replayed with the same encoder backend: a backend with more spans changes the text and misses the recording. The provider and its data residency: see "Single LLM" below |
| Knowledge retrieval evaluation | Measured on a **provisional synthetic** query set (120 validation queries per language, `data/eval/synthetic/retrieval/`), not a human-written one. Vector-only is the default backend (same-language Hit@1 0.494, cross-language 0.508, vs BM25 0.366 / 0.144; [ADR-0006](adr/0006-single-postgres-pgvector.md)). Banking-core `kb.search` serves the in-memory `packages/retrieval` index, built from vectors the model server returns (see "kb.search footprint"); pgvector ingestion remains pending. |
| Bare OTP in customer text | While an OTP challenge is pending, any standalone 4-8 digit run in the customer text is masked as an OTP (a small amount typed at that moment is over-masked, on the safe side). Outside a pending challenge, the regexes do not mask a bare code without a cue ("123456"); with the encoder up, `tfidf_lr` flags a lone six-digit number in a message of four words or fewer as a one-time code, so a six-digit amount typed alone is masked too (the safe side) |
| Encoder signal in the turn engine | The encoder runs first, on the raw customer text over the edge network (a local service, not a provider). The turn metadata records its intent, confidence and abstention, and only counts of its PII spans (`encoder_pii_spans`, `encoder_spans_added`; never offsets or text); its intent is not fed to the LLM (the decision points below ride on the same call and reach the LLM only as the categorical `CONFIRMATION_REQUIRED` refusal, and only when the gate enforces). Its PII spans widen the masking (see "Outbound PII masking"). Any encoder failure (unavailable, timeout, invalid payload, unexpected error) leaves the turn masked by the regexes alone and sets `encoder_unavailable` and `masking_regex_only`; with `ENCODER_ENABLED=false` the same masking is by configuration, not a degradation. Texts over 2,000 characters are outside the encoder contract and take the same path |
| Single LLM (GPT 6 Luna) | One model was chosen for the submission ([ADR-0001](adr/0001-cheap-llm-specialized-encoder.md), amendment 2026-09-29) for cost, tool support and access to a key, **not on comparative evidence**: `make eval` is not wired, so no tool-call, cost or latency number exists yet for it or for the DeepSeek candidates, now future work. It needs reasoning effort `none` to accept temperature 0; the `LLM_REASONING_EFFORT` setting is pending in PR #1 (`feat/llm-reasoning-effort`), and the model id and key are configured by the teammate who owns them. Masked conversations go to a US provider: a cross-border transfer with no data-processing agreement, retention or training-use terms reviewed, and no regional processing or zero-retention option in use. Replay recordings are keyed by model id and must be recorded with this model |
| Decision test split | Provisional: `decision.test.provisional.jsonl` was written free-form by an AI agent, not by humans, and has no double labeling. Calibration reports on it carry a "provisional synthetic (not human)" banner. The human set per [labeling-rubric.md](labeling-rubric.md) replaces it |
| Encoder abstention calibration | **Legacy seed mode only:** the committed calibration artifact (`packages/encoder/calibration/decision_points.json`, see the decision-point rows below) supersedes `ABSTENTION_THRESHOLD`, which the encoder then ignores and logs; the rest of this row is what holds when no artifact file exists. Boots in uncalibrated mode when ABSTENTION_THRESHOLD is unset (/health 200, /ready and /v1/analyze 503 "uncalibrated"); compose defaults it to the seed, so only an explicitly empty value does. Calibrated threshold tau is required before serving live traffic ([ADR-0010](adr/0010-model-selection-calibration-harness.md)). The seed value 0.37 is the highest per-language tau of `tfidf_lr` in `reports/calibration-decision-2026-09-28.md`, chosen on validation. On the provisional test split it does **not** hold the 0.90 per-class precision target (worst class 0.32 es, 0.53 pt, 0.40 en; macro-F1 0.79/0.84/0.79), so the encoder output is advisory only: the FSM and the policy engine decide ([ADR-0003](adr/0003-deterministic-vs-ai.md)). GLiNER zero-shot scores lower (macro-F1 0.47/0.43/0.52) at about 60× the RAM. A single global tau is stricter than needed for English |
| Encoder backends | `tfidf_lr` (lexical baseline) returns intents plus regex slots (email, card number, card last 4, OTP, amount, currency, dates) and PII spans for the PII-typed ones (email, card number, OTP, birth date); names, phones, document numbers, document types and merchants need `gliner`. The regex rules were tuned on the synthetic train and validation splits, and the provisional test split has the same author as the rules, so regex slot scores on it are optimistic until the human test set exists. `gliner` refuses to start when the cgroup memory limit is below `ENCODER_GLINER_MIN_MEMORY_MB` (default 4096); an unreadable or unlimited cgroup starts with a warning. `gliner` maps PII-typed slots to PII spans. Measured with `make encoder-bench` on the synthetic validation split (450 messages, single thread, Apple M-series host, 2026-09-27): `tfidf_lr` build 0.15 s, p95 0.22 ms, +43 MB RSS; `gliner` (`fastino/gliner2.5-multi-v1`, fp32) build 18 s, p95 90 ms, peak RSS 3.45 GB. The default demo backend is `tfidf_lr`; `gliner` needs `ENCODER_MEMORY_LIMIT=4g` (the compose default stays 3g), and `ENCODER_QUANTIZED` is read by compose but not implemented. The GLiNER weights of the legacy `ENCODER_BACKEND=gliner` path come from the Hugging Face cache by model id, without a pinned revision or hash yet (ADR-0010 §5); a `gliner` backend named in a decision-point artifact is pinned by revision (and optional hash) and loaded from the verified snapshot only, and on Linux PyTorch comes from the CPU-only index (`pytorch-cpu` in the root `pyproject.toml`; macOS keeps the default wheels for MPS training). The `gliner` image build has not been completed on the dev host yet (Docker disk full) |
| Delivered dataset in the seed | Loaded through `make ingest SOURCE=factored` ([ADR-0011](adr/0011-hybrid-seed-dataset-ingest.md)), capped at 5,000 customers by default (`INGEST_MAX_CUSTOMERS=0` for the full volume). Customers sharing a document, email or phone are dropped (about a third of the dataset repeats an email), and so are debit cards without an account in their currency; transaction coordinates are not loaded. Dates are shifted to end at `INGEST_ANCHOR_DATE`, so the history is realistic in shape but not in calendar. The ARS threshold is a seed derived once from the dataset's exchange rates. Counts per rule in `reports/data-quality-factored.md`. The intermediate `data/staging/factored/` files keep names, documents, phones and birth dates in clear text: they are local and gitignored, and only the curated load encrypts them |
| Policy configuration UI | Policy thresholds (`config.policy_config`) and the tool policy, the state × tool matrix (`config.tool_policy`), are versioned tables seeded from env on first read (ADR-0002); every change writes an audit row and applies to the next call without a restart. They are edited through the admin API (`/v1/admin/policy-config`, `/v1/admin/tool-policy`); the back-office UI for them is pending, and so are the other surfaces ADR-0002 lists (intents, message templates, queue priority), which are not configuration tables yet. |
| Admin API | `/v1/admin` uses bearer-token auth; demo fixture resets are disabled in production unless explicitly enabled. The development compose turns the API on with the public token `dev-only-admin-token` so the demo works with no `.env`; `banking-core` refuses to start with that token (or an empty one) under `APP_ENV=production`, and the production compose pins the API back to off. |
| Amount guardrail needs the model to link the charge | The amount comes from the database, but only for the `transaction_id` the model passes to `card.block` ([ADR-0003](adr/0003-deterministic-vs-ai.md), amendment 2026-09-29). A `UNRECOGNIZED_CHARGE` or `SUSPICIOUS_ACTIVITY` block without one fails safe into a required handoff. A `LOST`, `STOLEN` or `CUSTOMER_REQUEST` block without one is compared with no amount, so a model (or a customer steering it) that picks such a reason and omits the link is not checked against the threshold. banking-core does not yet look at the card's recent charges by itself, so a model (or a customer steering it) that links a different, smaller real charge of the same card lowers the outcome as well. The `risk_threshold` scenarios assume the model finds the charge by the merchant name the customer gives and links its `transaction_id`; that step has not been observed: nothing has run against a live or a replay LLM yet, the scenarios were checked only against the deterministic parts (policy, lookup, engine with a scripted model). A `transaction_id` on `handoff.create` is honored only in a verified session; in any other state it is dropped, so the handoff carries no charge facts |
| Recommended handoff is advisory | Above the threshold, mode `flag` (handoff recommended) returns the recommendation to the model, which may offer a human; nothing creates the handoff. Only mode `block` (handoff required) is enforced: the orchestrator engine creates the handoff when the model did not, and banking-core never lets the model lower its priority. The engine tries its write once per turn and retries on the next customer message: if the write fails and the customer sends nothing more, the card is blocked, the block is audited with its `HANDOFF_REQUIRED` flag, but no handoff exists in the queue. The engine also reads the charge to link from the recorded tool call, so if that call's arguments failed masking the handoff is still created but without the charge facts |
| Amount mode names | The stored values are `flag` and `block`; the docs call them "handoff recommended" and "handoff required" because `block` does not block anything (`card.block` is never refused for amount). Renaming the stored values to `recommend` and `require` is pending (AGENTS.md) |
| One-command demo | `make demo` has not been run against a real Docker daemon yet (its script was only dry-run against stubs) and still needs the clean-machine pass in the [runbook](runbook.md) checklist. It re-seeds on every run: the demo customers' cards return to their seed state and the handoff queue is emptied. Without replay recordings (none exist yet) or an LLM key a chat turn answers 503, and `make demo` says so. The web client that will show simulated OTP codes is pending, so a local run reads them through the dev hook (`ALLOW_DEV_OTP_HOOK=true`). |
| Read tools vs contract | `account.get_summary` omits balance values as null when `include_balances=false`. `transaction.list_recent` lists card transactions only, because each item requires a `card_ref`. `card.list` returns `expiry_month`/`expiry_year` as null for synthetic cards (no source data) and derives `card_type` from the account (CREDIT_LINE → CREDIT, otherwise DEBIT) until stored values exist |
| Audit log tail truncation | Tail truncation with the owner disabling triggers is only detectable against an external count/head_hash checkpoint. |
| OTP inbox and test hook | Codes live in the simulated inbox on redis-core, not in process memory (`otp:inbox:` keys, one entry per challenge that expires with it, plus a per-session index of at most 10; [docs/deployment.md](deployment.md)). The clear code is never logged and is absent from tool results, audit payloads, LLM history, transcript and turn metadata. It is readable, for the challenge TTL (`OTP_TTL_SECONDS`, 300 s by default), by whoever holds the banking session id through `GET /v1/sessions/{id}/simulated-inbox` (internal to `banking-core`, its access log redacts session ids) and by whoever holds the conversation id through the orchestrator's `GET /v1/conversations/{id}/inbox`: controlling the conversation is enough to read its code. A code stays in the inbox after it is used, until it expires. An explicit test/dev-only hook, `GET /v1/dev/otp/{challenge_id}`, reads the same store across sessions for the evaluation runner; it is disabled by default, only mounted when `ALLOW_DEV_OTP_HOOK=true`, and `banking-core` refuses to start with it enabled when `APP_ENV=production`. The `/inbox` route has no limit of its own beyond the conversation id being unguessable |
| Session state vs database commit | The session is saved to Redis after the database commit, and an OTP code is delivered before its audit row commits. If the commit or the save fails in between, the session does not advance (fail closed): a delivered code cannot be verified because the session never reached OTP_PENDING, and a retry with the same idempotency key replays the recorded result without advancing the session, so the step has to be repeated with a new key. A delivered code can exist without an audit row. A transactional outbox for delivery and session writes would close it; "one open handoff per session" is held by the session lock plus a per-session advisory lock, not by a database constraint |
| `customer.match` timing | A miss spends one decrypt like a hit with birth date, but a miss still probes every equivalent document type (one extra indexed query in the pt market); no constant-time padding of DB round trips. Since the per-document limit, every match also spends one Redis round trip to count itself, on a hit and a miss alike (a hit then gives the count back in a few more, but a hit already differs in its answer). A match past the limit skips the lookups altogether, so it is faster than a miss: that depends on the document's counter only, never on whether the document exists, but it is a timing difference and no padding hides it |
| Attempt limits across sessions | Per customer (failed `otp.verify`, [ADR-0004](adr/0004-trust-boundary.md) amendment 2026-09-29) and per claimed document (failed `customer.match`), counted on redis-core in fixed windows opened by the first failure. Up to twice a maximum can fall around a window boundary, and the customer counter is not reset by the lock or by a successful verify (it ages out). Thresholds are policy configuration seeded from `RATE_LIMIT_CUSTOMER_OTP_*` and `RATE_LIMIT_DOCUMENT_MATCH_*`; rows already in `config.policy_config` take the migration defaults (5 / 3600 s / 1800 s / 10 / 3600 s) and the Admin API does not expose them yet (a new version is saved through `save_policy_config`). **The lock is a denial-of-service lever**: someone who fails five codes for a customer, or ten matches for a document, blocks that customer's OTP or that document's matches for the window; the way to a human is never limited. The lock check and the delivery are not one atomic step: a concurrent session's `otp.send` that passed the check just before the lock can still deliver one code, which cannot be verified while the lock holds. Redis counters move before the database commit, like the session (see the row above): a failed commit keeps the count and can lose the audit row of a lock event. Invalid document formats have no blind index and are counted per session only. The fixture reset of the demo Admin API forgets the fixture customers' counters, not other documents' |
| Per-IP limit on conversation creation | `POST /v1/conversations` is limited per client address at the orchestrator (fixed one-hour window on redis-edge, 429 with `Retry-After`; 30 by default in the orchestrator and in the production compose, 1000 in the development compose so a local session or an evaluation run does not hit it; redis-edge down answers 503, fail closed). It is only as good as the address it sees: **behind a reverse proxy `TRUSTED_PROXY_HOPS` must be set** to the proxy count, or all customers share one budget; set too high, the client picks its own bucket. `X-Forwarded-For` is ignored by default. IPv6 is grouped by /64. Customers behind one NAT (an office, a demo room, the evaluation runner, which opens one conversation per scenario: `make eval` ⚠️ pending) share a budget: raise `RATE_LIMIT_CONVERSATIONS_PER_IP_HOUR` for them. The setting must be at least 1: `0` is rejected at startup, it does not mean unlimited |
| U6 evidence in the proposed-system eval | Unmasked-PII-to-provider (U6) evidence comes from the orchestrator side: the masked outbound messages its eval hook exposes, and the replay recordings on disk. Neither is the trusted side; the report labels the provenance. Without the hook, U6 stays "needs human review" and a replay miss cannot be told apart from other turn failures, so it counts as a failure (only a 503 with detail "replay_miss" is reported as not run) |
| kb.search footprint | The vector backend (default) embeds through the **model server** (`apps/encoder`, `POST /v1/embed`; [ADR-0012](adr/0012-decision-points.md), Appendix J). banking-core builds the 120-snippet index in memory from vectors the server returns and embeds each query there; in the default configuration it never imports torch or sentence-transformers, so the ~1.3 GB RSS that MiniLM plus the index cost there (measured on macOS; the Linux container figure is pending, on either side) is not in the trusted zone any more. The model server holds the model once for every replica; it should fit its 3 GB limit with `tfidf_lr` (estimate). **Still in the image:** banking-core is built with the `vector` extra (image 2.05 GB, 528 MB without; linux/arm64, CPU-only torch, measured before this change) because the local backend (`EMBEDDING_BACKEND=local`, tests and local development only) needs it and no container build could be run in this change; dropping it is `BANKING_CORE_SYNC_ARGS=""` after a clean-machine `make demo`. **Pins:** the model is `EMBEDDING_MODEL` at a full 40-hex `EMBEDDING_REVISION`, verified against the model server's cache before it loads, and banking-core compares the model and revision on every answer; a mismatch, an unreachable server or a swapped model makes kb.search unavailable, never a fallback to BM25 or a local model. `EMBEDDING_WEIGHTS_SHA256` (hash of the weights file) is optional and unset by default; `make warmup-retrieval` prints it. **The default revision `86741b4e3f5c...` was written from memory and could not be verified** (huggingface.co is unreachable from the environment this was built in): if `make warmup-retrieval` fails with a revision error, replace `EMBEDDING_REVISION` with the hub's current commit and confirm the hash it prints. The model comes only from the model server's `hf-cache` volume (`make warmup-retrieval`); without it `/v1/embed` answers 503 with the reason and kb.search fails loudly. The same-to-cross-language score floor (0.3) is an uncalibrated seed. The production compose mounts `hf-cache` in the model server, but **nothing fills that volume on a server**: `make warmup-retrieval` is a local target and `deploy.yml` does not run it, so on a deployed stack kb.search fails loudly until the volume is filled by hand on the model host. The deploy workflow now builds the encoder image with `ENCODER_EXTRAS=embed` by default; an image built with the extras emptied refuses to start while `EMBEDDING_MODEL` is set |
| Model server: access, trust and availability | The model server receives **raw customer text** (`/v1/analyze` runs before masking) and kb.search queries. It must stay inside the team's private network and is never a third-party service; in production compose it publishes no host port. **There is no authentication and no TLS between the orchestrator or banking-core and the model server**: the network is the only control, and any host on that network can call it. banking-core now depends on it for `kb.search`, an **integrity** dependency of the trusted zone on a service that lives on the `edge` network: a compromised or wrong model server can return bad vectors and make kb.search rank a wrong *public* KB snippet first. It cannot change an authorization, a receipt or a write, and it holds no credential and has no path to the database. banking-core checks the model and revision of every answer, the vector count, the dimension and finiteness, and re-normalizes each vector (a zero vector is refused), so a swapped model or a malformed answer is caught; **plausible wrong vectors from a model server that reports the right identity are not**. One model server, no replicas, no failover: if it is down, `/v1/analyze` degrades as before (the orchestrator continues LLM-only) and kb.search is unavailable |
| Decision points, encoder side ([ADR-0012](adr/0012-decision-points.md)) | The model server evaluates decision points from a calibration artifact and returns `decisions` beside the legacy fields, and ships a seed artifact written by the harness (`make calibrate TASK=decision-points`; checked statically by `make calibration-verify`), whose evidence is provisional (row "Calibration evidence is provisional" below). Only when no artifact file exists does it fall back to legacy seed mode, one uncalibrated `turn_intent` from `ABSTENTION_THRESHOLD`, exactly the legacy answer; with the artifact that variable is ignored. The orchestrator consumes `decisions` through the effects described in the next row; the scenarios are a separate work package. `packages/encoder/tests/fixtures/` holds a test artifact whose numbers were picked, not fitted: it is not a calibration. Backends: `tfidf_lr` and `gliner`; `llm_sidecar` fails at startup with `pending: llm_sidecar is not implemented (ADR-0012)`; the isotonic calibrator and `escalate_to` (cascading) are refused as pending. A group view is never renormalized over its view, so an utterance outside it abstains. A decision-point backend that runs longer than its `timeout_ms` is reported `unavailable` but its worker thread keeps running (a CPU-bound call cannot be interrupted), so a hung adapter can exhaust `DECISION_POINTS_MAX_WORKERS` and make every later decision `unavailable` until the service restarts. Artifact `train.path` files must exist in the encoder image: only `data/eval/synthetic/decision.train.jsonl` is copied today |
| Decision points, orchestrator side ([ADR-0012](adr/0012-decision-points.md)) | The engine loads `apps/orchestrator/config/decision_effects.yaml` at startup (an invalid file stops the service; `route_tools`, `canned_reply`, `propose` and `hint` are rejected as pending) and applies three effects: `record`, `select` (an enum argument of an LLM-proposed call, never `priority`, `card_ref` or a secret) and `gate` (withholds `card.block` until the customer consents). **Every decision point ships in `shadow`**: the decisions and what each effect *would* have done are recorded in the turn metadata and reported per language by the evalrunner, and nothing else changes. The encoder serves all five decision points from the committed artifact; if its file is missing it serves only `turn_intent` (legacy seed mode), and `confirm_gate`, `block_reason`, `handoff_route` and `smalltalk_route` are then recorded as `unavailable` (`not_served`) and even an `enforce` gate could only be opened by an explicit request. The orchestrator asks only for ids the encoder lists (a stale listing costs one repeated call, never the PII spans). Editing the effects file is by pull request; there is no back-office editor. The decisions do not use the concurrent analysis of ADR-0012 E.1: the encoder's PII spans are needed before the masking, which precedes the first LLM call, so the decision points ride on that same call and add no request. `PROMPT_VERSION` moved to `turn-engine/2` (one explanatory line for `CONFIRMATION_REQUIRED`) without a `make eval` before and after, because `make eval` is a pending target; no replay recordings existed to invalidate, and the ones recorded for the freeze must use this prompt |
| The gate is a control, not an authorization | It runs in the untrusted zone. banking-core still requires `VERIFIED`, ownership and an idempotency key for every block and knows nothing about the customer's consent, so an orchestrator compromised or bypassed can call `card.block` without it. Its value is against an over-eager or misled model, not against an attacker who controls the orchestrator. A gate enforced by banking-core is future work |
| Consent is per tool, not per card, and one block spends it | The customer's yes, or an explicit request, lets the *next* `card.block` through, whichever card the LLM names among the customer's own (banking-core's ownership check still applies), and a successful block consumes it: "block both cards" needs a second confirmation. A card-scoped consent is not built. Consent and an open question expire after `max_age_turns` (6) turns; a decided `deny` closes both and beats an explicit request in the same turn |
| Decision provenance is not in the audit chain | The consent source, the deciding model and its `config_version` are recorded in the turn metadata (the stored message metadata on redis-edge, which expires with the session), not in banking-core's audit chain, which records the call with its effective arguments (so the block reason is audited as before) but not why. The orchestrator cannot write the chain. A `ToolCall.provenance` field, stored as unverified, would close it |
| All decision points in `shadow` until the calibration owner signs off | Flipping one to `enforce` is its own reviewed diff after the sign-off of ADR-0012 Appendix F, with the evaluation report attached and this row updated. The calibration evidence is provisional (the 10-rows-per-class test split cannot certify precision 0.95; the reports say "certified: no"; the numbers are in the next row). While the gate enforces, a model that abstains on a colloquial yes ("síp"), or an encoder that is down, costs an extra turn (fail-closed by design: [ADR-0012](adr/0012-decision-points.md) trade-off analysis), and a customer who clearly commands the block is served in one turn only if `turn_intent` decides `request_card_block` |
| Calibration evidence is provisional, decision point by decision point | The seed artifact and `reports/calibration-decision-points-2026-09-29.md` come from a synthetic train and validation set and an AI-written test split (10 rows per intent and language, never double-labeled). Thresholds were chosen on validation by the point estimate of precision (`ci: point`) with `n_min` lowered to 10, or 30 for the two pooled `select` decision points, because the Wilson bound is infeasible there; **all five decision points are `calibrated` and none is certified** (0 of 21, 6, 5, 4 and 6 scopes clear the Wilson 95% lower bound: 22 correct of 22 reaches only 0.85, and 0.95 needs 73 accepted rows with zero errors). Validation shares its generating process with train, so the calibrators are over-confident on real traffic. `turn_intent`: test coverage 77.3% es, 58.0% pt, 99.3% en (36.7%, 28.0% and 50.0% on the acted labels), ECE 0.086, 0.064 and 0.085 after temperature (about 0.5 before); the en threshold rejected nothing on validation (it is only the lowest confidence seen), and 9 acted label-and-language scopes are below the 0.90 floor even by the point estimate, worst en `report_lost_card` 10/15, en `report_suspicious_activity` 9/13 and en `request_human_agent` 10/14. `confirm_gate`: no false `confirm` on test (21/21 pooled) but recall only 0.70 (8 of the 30 test confirms are decided `other` and 1 abstains), and each miss costs the fail-closed gate an extra turn; `deny` is below its 0.90 floor (22/26 pooled, 9/11 in es and pt); its thresholds bound nothing on validation, and with no hard-negative set false accepts on hard negatives are unknown, not zero. `block_reason`: `LOST` 24/29, `STOLEN` 27/31, `SUSPICIOUS_ACTIVITY` 26/31 and `CUSTOMER_REQUEST` 25/29 (0.83 to 0.87) are below the 0.90 floor; only `UNRECOGNIZED_CHARGE` reaches it (10/10, recall 0.33). `handoff_route`: `HUMAN_REQUEST` 30/49 = 0.61 against 0.90 and `FRAUD` 54/63 = 0.86 are below it; `DISPUTE` 23/25 and `UNRECOGNIZED` 10/10 are not. `smalltalk_route`: `out_of_scope`, the known sink, is 17/27 = 0.63 against 0.95 (0.62 to 0.64 per language), which is why it only records. Latency and RAM in the report are host measurements of one process, not the container limits (`make encoder-bench` for artifact backends is pending). **Every decision point stays in `shadow`**; a flip to `enforce` needs the sign-off of ADR-0012 Appendix F.5 (the constraint met on test with the Wilson bound, or the exact shortfall written here) and its own reviewed diff |
| Intents and decisions no decision point covers | No acted label lacks a threshold: the artifact records `evidence.uncovered = []` for all five decision points, so none abstains in a language for lack of one (a non-empty list, written `lang/label`, would belong here). What is uncovered is different. `turn_intent`'s constraint binds 7 of the 15 intents (the report, block-request and human-routing intents that the ledgers and the explicit request read); the other eight (`check_balance`, `check_recent_transactions`, `confirm`, `deny`, `greeting`, `out_of_scope`, `provide_identity_data`, `provide_otp_code`) are decided at the same threshold with no precision floor and no effect reads them (pooled test precision: `out_of_scope` 0.50 and `provide_otp_code` 0.81, the rest 0.91 to 1.00). The `other` labels of `confirm_gate` and `smalltalk_route` decide whenever they are on top and are not constrained. The LLM still chooses alone which read tool to call (`check_balance`, `check_recent_transactions`), and identity and OTP handling has no decision point on purpose (the FSM and the masking handle it, ADR-0012 Appendix A); `handoff.create.priority` is never selected by a decision point (the policy engine decides it) |
| `out_of_scope` is not used to act | `smalltalk_route` only records: the 15-way model sends bare OTP digits, "nope" and "holaa" to `out_of_scope`, and a customer who writes "hola, me robaron la tarjeta" must not be stranded. The offline metric is the share of turns where it decided `greeting` or `out_of_scope` while the LLM called a tool |
| Scenarios for the decision points | The scenario schema cannot switch orchestrator modes per scenario, so there are no `enforce` scenarios and no `gate_breach`, `gate_false_consent` or `gate_extra_turns` numbers: the report shows coverage, abstention and unavailability per decision point and what the gate and the selects *would* have done in `shadow`. The nine gate scenarios and `eval/replay/DECISION_CONFIG` of ADR-0012 Appendix G are pending |
| Fonts and the design-system sync | The typography loads from Google Fonts (no font files in the repository): without a network the front ends use the fallback stacks, so the title card is set in a system serif instead of Noto Serif Display at its narrowest width, and the demo needs internet for the intended look. `packages/design-tokens` is a checked copy of a published design-system artifact, synced by hand (no script reads the artifact); `make design-tokens-check` catches a stale `dist/` and a missing variable, not a stale `src/`. Contrast and token use are the artifact's claim, not tested here ([packages/design-tokens/README.md](../packages/design-tokens/README.md)) |
| TypeScript contracts | `@pattern-blue/contracts` mirrors the message blocks and the enums in Zod and a drift test compares them with the JSON Schemas exported from Python. The HTTP shapes of the chat, agent and admin APIs are mirrored by hand: their Pydantic models live in the apps, no JSON Schema is exported for them, so a change on the Python side is caught only by the front ends' tests against fixtures, not by a drift test ([packages/contracts/README.md](../packages/contracts/README.md)) |

## 3. What we did not do

| Not done | Why |
|---|---|
| Autonomous dispute resolution | A judgment call with monetary impact: our test case for not automating |
| Real biometrics | Requires a certified provider with liveness detection |
| Voice channel | A different problem (transcription, latency, barge-in); adds nothing to the chosen workflow |
| Onboarding and credit origination | Outside the workflow |
| Load testing | We prioritized correctness over performance in the available time |
| Per-IP rate limiting in banking-core | Banking-core cannot trust a client address relayed by the untrusted orchestrator; per-IP limiting belongs at the edge, where it exists only for conversation creation (§2) |
| Per-IP limit on messages, and distributed attackers | Sending messages, opening conversations from many addresses, and any attacker with more addresses than the per-IP budget are not limited per address. What bounds them is the per-customer and per-document limits (a fixed number of OTP guesses per customer and of match guesses per document, however many addresses guess) and the per-session limits. No CAPTCHA, no reputation feed, no anomaly detection |
| Limit on `otp.send` volume across sessions | A resend limit exists per session and a locked customer gets no code, but nothing limits how many codes different sessions can trigger for one customer before the lock (unrelated to failed verifies): an SMS-bombing and delivery-cost vector. Needs a per-customer send counter |

## 4. Known failure modes

**TODO at close.** The ones we already anticipate and must confirm or rule out with data:

- Degradation in Portuguese relative to Spanish in the classifier, if the labeled sample came out unbalanced
- Cross-language retrieval: question in one language, knowledge in another. Measured: vector-only Hit@1 0.508 (mean es/pt/en) against an index restricted to the other languages; BM25 0.144. Same-language search is the default, so this only matters when the KB lacks the customer's language
- Long conversations: context grows and so do cost and latency
- Ambiguity between neighboring intents: TODO, per the confusion matrix
- Unnecessary escalation on legitimate but unforeseen cases: a cost the design accepts ([ADR-0003](adr/0003-deterministic-vs-ai.md))

## 5. What we would do with four more weeks

1. **A real document verification provider**, with thresholds and retry policy.
2. **KMS or HSM** for the master key, with scheduled rotation.
3. **Human-in-the-loop learning**: every agent correction in the back office becomes a labeled example, with periodic retraining and drift monitoring.
4. **Continuous evaluation in production**: sampling real conversations for human review, not just a fixed suite.
5. **Load testing and a read replica** before exposing the system to real volume.
6. **Expand the adversarial suite**, with injection in fields we do not currently treat as hostile.
7. **Full multi-tenancy** on top of the schema separation already anticipated.

## 6. Where else this applies

The engine is not banking-specific. The same core — calibrated classification with abstention, verification state machine, policy engine, structured handoff and audit — applies to any customer service domain where an action has irreversible consequences: telecommunications, insurance, healthcare, logistics. What changes is the tool catalog; the control does not.
